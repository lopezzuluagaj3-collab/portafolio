1. Resumen general

⚠️
Estado del Proyecto: Fuera de Producción / Archivado. La infraestructura activa fue desmantelada al concluir el ciclo de evaluación y entrega; esta documentación preserva la arquitectura, decisiones de hardening y bitácora técnica de lecciones aprendidas.

VPS única (4 GB de RAM) alojando el stack completo del proyecto Idempotencia: un producto gestor de bases de datos para usuarios finales (por eso corren 4 motores de DB). Incluye frontend, backend (producción y QA), y cuatro bases de datos, todo detrás de Nginx Proxy Manager (NPM) con SSL de Let's Encrypt. El acceso administrativo (SSH, bases de datos, paneles internos) está cerrado al público y se gestiona mediante Tailscale (VPN privada) y port knocking.

IP pública de la VPS: <IP_PÚBLICA_VPS>    IP privada (Tailscale) de la VPS: <IP_PRIVADA_TAILSCALE>

Modelo de producto: los usuarios finales de Idempotencia necesitarán conectar sus propias herramientas externas (Airflow, DBeaver, etc.) directamente a bases de datos gestionadas, con credenciales propias — no solo a través de la app web. Esto implica que, a futuro, algunos puertos de base de datos deberán exponerse de forma controlada (ver Pendientes abiertos).

2. Firewall — estado actual y hallazgo crítico

2.1 Hallazgo de seguridad: Docker bypassea ufw

Se descubrió que Docker inyecta sus propias reglas en iptables (cadenas DOCKER / FORWARD) al publicar un puerto con ports: "0.0.0.0:PUERTO:PUERTO" en un docker-compose.yml. Estas reglas son independientes de ufw y se evalúan aparte — por lo que un puerto podía estar públicamente accesible desde internet aunque ufw status no mostrara ninguna regla ALLOW para él. Es un conflicto conocido entre Docker y ufw.

Esto se confirmó como la causa de un ataque de fuerza bruta real detectado contra el usuario sa de SQL Server, pese a que el diseño original asumía que ese puerto ya estaba restringido solo a Tailscale.

Método de verificación en 3 capas (auditoría obligatoria ante dudas de exposición):

docker ps                                          # qué publica Docker
sudo ss -tulnp                                      # qué escucha realmente el host
timeout 2 bash -c "echo > /dev/tcp/<IP_PÚBLICA_VPS>/<puerto>" && echo "ABIERTO" || echo "cerrado"

2.2 Patrón de corrección aplicado

En cada docker-compose.yml afectado, cambiar:

# Inseguro:
ports:
  - "0.0.0.0:PUERTO:PUERTO"

# Corregido y aislado:
ports:
  - "<IP_PRIVADA_TAILSCALE>:PUERTO:PUERTO"   # solo accesible vía Tailscale

Y recrear con: docker compose up -d --force-recreate <servicio>. Esto no afecta la comunicación interna entre contenedores (que usa el nombre de contenedor sobre la red Docker red-proxy, no el binding público), ni requiere tocar volúmenes.

2.4 Hardening base del sistema

  • PermitRootLogin no, PasswordAuthentication no (solo login por llave SSH Ed25519/RSA).
  • Usuario dedicado devop con permisos sudo controlados.
  • fail2ban activo (jail sshd).
  • CrowdSec instalado como capa de detección y bloqueo activo en kernel.
  • unattended-upgrades instalado para parches automáticos de seguridad.

3. Acceso remoto

3.1 SSH — Port knocking

El puerto 22 permanece cerrado por defecto en el firewall. Para conectarse:

  1. Se ejecuta el script PowerShell (conectar.ps1) que:
    • Envía una secuencia de paquetes TCP a los puertos 7000, 8000, 9000 para abrir el 22.
    • Lanza automáticamente la sesión SSH con llave privada autorizada.
    • En segundo plano, tras un tiempo de espera configurable (15s), envía otra secuencia (6000, 5000, 4000) para volver a cerrar el puerto en iptables — sin interrumpir la sesión establecida.
  2. Cada miembro del equipo con acceso requiere su propia llave autorizada en ~/.ssh/authorized_keys de la VPS.

4. GitHub / control de versiones

4.1 Organización

Organización dedicada donde solo el rol DevOps (Juan) cuenta con privilegios administrativos.

4.2 Estrategia de ramas

feature/* ──► develop ──► QA ──► main
  • main: producción, desplegada automáticamente en la VPS vía GitHub Actions.
  • QA: ambiente de pruebas también desplegado en la VPS en puertos dedicados.
  • Solo los roles QA y DevOps tienen permiso de push/merge a main y QA.

4.3 Branch protection rules

  • Pull request obligatorio antes de mergear.
  • Restricción de push y merge limitada al team qa-devop.
  • Bloqueo estricto de force-push y eliminación de ramas críticas.

8. Incidentes resueltos (bitácora)

8.1 Error 500 en /auth/register — connection string con IP pública

Síntoma: Timeout de conexión SQL (SqlException) al registrar un usuario.

Causa: La connection string apuntaba a Server=<IP_PÚBLICA_VPS> en vez de Server=idempotencia-sqlserver, cayendo en un bloqueo por hairpin NAT.

Solución: Corregir el servidor al nombre del contenedor en la red Docker. Conexión restablecida de inmediato con latencia <1ms.

8.2 Volumen duplicado de SQL Server al recrear el contenedor

Síntoma: Al aplicar --force-recreate, Docker creó un nuevo volumen vacío ocultando los datos reales por discrepancia en el nombre de la carpeta.

Solución: Backup preventivo inmediato vía T-SQL (.bak), extracción de los 8 procedimientos almacenados, purga del volumen vacío y declaración explícita de volumen externo:

volumes:
  sqlserver-data:
    external: true
    name: idempotencia-db_sqlserver-data

Resultado: Cero pérdida de datos.

8.3 appsettings.json montado como directorio

Docker crea un directorio si el archivo no existe en el momento del primer bind mount. Corregido eliminando la imagen y reconstruyendo con docker compose build --no-cache.

8.4 Permisos del appsettings.json (chmod 600 vs 644)

El proceso dentro del contenedor corre como usuario no-root app. Un permiso 600 bloqueaba su lectura. Se ajustó a 644 montado como solo lectura.

9. Backups y persistencia

Respaldos realizados (ad-hoc):

  • Backup completo de SQL Server (.bak) en /home/devop/idempotencia-db-sqlserver/.

11. Kubernetes — evaluado y descartado por ahora

Se evaluó migrar los contenedores a Kubernetes (k3s). Conclusión técnica: no es viable en el servidor actual. La VPS es un solo nodo físico de 4 GB de RAM, y K8s consume entre 1.0 y 1.4 GB únicamente para su plano de control (API server, etcd, kubelet) sin aportar tolerancia a fallos entre máquinas.

Se continuará con Docker Compose optimizado y se reevaluará Kubernetes gestionado solo si el proyecto escala a múltiples servidores físicos.

12. Lecciones operativas (referencia rápida)

  • Docker bypassea ufw al publicar puertos: verificar siempre con ss -tulnp y pruebas TCP reales.
  • Las cadenas de conexión dentro de contenedores deben usar siempre el nombre del contenedor, nunca IPs públicas.
  • Antes de un --force-recreate con datos persistentes, verificar con docker inspect cuál es el volumen en uso y declararlo external: true.
  • Un contenedor en estado "Up" no garantiza servicio: validar con logs y pruebas de conexión internas.
