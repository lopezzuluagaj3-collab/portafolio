🌌 Proyecto Pléyades — Plataforma Cloud-Native SaaS en Azure

Plataforma SaaS empresarial Multi-Tenant de alto rendimiento en Microsoft Azure (`eastus2` / `centralus`), gobernada 100% mediante GitOps pull-based con ArgoCD, Internal Developer Platform (IDP) con Crossplane, microservicio hexagonal en Go 1.24 y modelo matemático de confiabilidad SRE (Ley de Little). 

[METADATOS DE PLATAFORMA]
Autor: Juan Diego López Zuluaga (DevOps, Cloud Platform & SRE Senior Engineer)
Cloud Provider: Microsoft Azure (eastus2 / centralus)
Arquitectura: 3 Repositorios Desacoplados (IaC, GitOps & Microservicio Go 1.24)
Confiabilidad SRE: Modelo analítico Ley de Little (p95 < 1500 ms @ 50 VUs)
Contenedor: Distroless OCI (10.3 MB en GHCR) | Zero Static Secrets (Azure OIDC)

Los 5 Pilares Arquitectónicos de Pléyades

  • Gobernanza Declarativa GitOps (Pull-Based): Eliminación total de despliegues push desde CI. ArgoCD reconcilia y autorrepara continuamente el estado vivo del clúster AKS.
  • Internal Developer Platform (IDP) con Crossplane: Auto-escalado horizontal de bases de datos relacionales en la nube. Al superar el umbral preventivo (5/7 tenants), la app dispara la provisión autónoma de nuevos servidores Azure PostgreSQL Flexible Server vía Custom Resources.
  • Multi-Tenancy con Aislamiento Estricto (Database-per-Tenant): Cada cliente cuenta con su propia base de datos PostgreSQL, usuario dedicado con contraseña efímera (Show-Once Pattern), revocación estricta (REVOKE CONNECT ON DATABASE ... FROM PUBLIC) y cuota estricta (CONNECTION LIMIT 2).
  • SRE & Modelo Matemático de Capacidad: Dimensionamiento del pool de conexiones contra límites reales de B1ms (35 conns utilizables, pool=3/pod) y derivación de latencias por la Ley de Little en sistema cerrado ($R = \frac{N}{\lambda} - Z$).
  • Zero Static Secrets: Azure Workload Identity y Entra ID mediante federación OIDC en Terraform, GitHub Actions y Crossplane.

Topología del Ecosistema (3 Repositorios)

pleyades-infrastructure/   ──► Terraform Modular, AKS (Cilium eBPF KPR), Blob Storage tfstate
pleyades-gitops/           ──► ArgoCD App-of-Apps, Crossplane Provider v2.8.4, Stack SRE
pleyades-app/              ──► Go 1.24 Hexagonal, pgx/v5, Distroless (10.3 MB), Suite k6
Repo: Infrastructure ➔ Repo: GitOps ➔ Repo: App SaaS ➔

1. Arquitectura de Infraestructura como Código (IaC)

Aprovisionamiento declarativo e idempotente de la infraestructura base en Azure mediante Terraform modular, state locking nativo con Azure Blob Leases, federación OIDC con Entra ID y bases de datos gestionadas.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 02: Estructura Modular y Scaffolding Inicial en Terraform

  • Estado: Aceptado e Implementado.
  • Decisión: Estructurar el repositorio de infraestructura desacoplando la raíz mediante la carpeta modules/ (networking, aks, resource_group, identity), cada uno con main.tf, variables.tf, outputs.tf y locals.tf.
  • Justificación: Alta cohesión, bajo acoplamiento y reducción drástica del radio de impacto (blast radius), validando la tubería de CI/CD desde el primer commit.

📌 ADR 03: Gestión de Estado Remoto en Azure Blob Storage

  • Estado: Aceptado e Implementado.
  • Decisión: Configurar el backend en un Azure Storage Account dedicado dentro de un Resource Group aislado (rg-pleyades-tfstate), con contenedor Blob para tfstate.
  • Justificación: Aislamiento de privilegios para metadata sensible y bloqueo nativo concurrente (State Locking) mediante Azure Blob Leases para evitar corrupción de estado en ejecuciones simultáneas.

📌 ADR 04: Seguridad "Zero Static Secrets" mediante OIDC y Federated Credentials

  • Estado: Aceptado e Implementado.
  • Decisión: Eliminar el uso de contraseñas o Service Principal Secrets. Se implementan Federated Identity Credentials sobre una User-Assigned Managed Identity (UAMI) en Microsoft Entra ID.
  • Lección Técnica Crítica (Immutable Subject Claims): GitHub emite tokens OIDC con formato inmutable (repo:<org>@<org_id>/<repo>@<repo_id>:<context>) para prevenir suplantación si se renombra la organización. Entra ID exige coincidencia estricta; omitir los IDs numéricos dispara el error AADSTS700213.
  • Credenciales Federadas Configuradas:
    1. Pull Requests: repo:<org>@<org_id>/<repo>@<repo_id>:pull_request (para validación y terraform plan).
    2. Rama Principal: repo:<org>@<org_id>/<repo>@<repo_id>:ref:refs/heads/main (sincronización tras merge).
    3. Producción: repo:<org>@<org_id>/<repo>@<repo_id>:environment:production (para ejecución controlada de terraform apply).

📌 ADR 30: Azure PostgreSQL Flexible Server en Región Habilitada (centralus)

  • Estado: Aceptado e Implementado.
  • Decisión: Aprovisionar Azure Database for PostgreSQL Flexible Server (psql-pleyades-dev-01) en centralus con SKU Burstable Standard_B1ms, TLS obligatorio (require_secure_transport = on) y regla de firewall allow-azure-internal (0.0.0.0 - 0.0.0.0).
  • Hallazgo de Cuota Regional: Azure restringe nuevas instancias Flexible Server en eastus2 para suscripciones estándar/estudiante (código ParameterOutOfRange: supportedServerVersions: []). centralus soporta versiones 11 a 18 sin restricciones. Se asumió la regla 0.0.0.0 en desarrollo para eludir el coste de un VNet Peering transcontinental.

2. Cómputo AKS y Networking eBPF con Cilium

Plano de datos de ultra-alto rendimiento en Kubernetes mediante Kube-Proxy Replacement (KPR), mapas BPF $\mathcal{O}(1)$ en el kernel de Linux y análisis de gobernanza de cuotas de cómputo en la nube.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 06: AKS con Cilium eBPF, Standard_D2s_v7 y CIDRs Desacoplados

  • Estado: Aceptado e Implementado.
  • Decisión: Aprovisionar aks-pleyades-dev utilizando:
    1. Node Pool & SKU: Standard_D2s_v7 (2 vCPUs, 8 GiB RAM) con autoescalado 1 a 2 nodos en dev, y min_count = 2 en el perfil de producción multi-nodo (ADR 22).
    2. Data Plane: Azure CNI Overlay con Cilium eBPF nativo y Kube-Proxy Replacement (KPR).
    3. Desacoplamiento de CIDRs: Asignación explícita de service_cidr = "172.16.0.0/16", dns_service_ip = "172.16.0.10" y pod_cidr = "10.244.0.0/16".
    4. Seguridad Cloud-Native: OIDC Issuer y Azure Workload Identity activados.
  • Hallazgos Críticos:
    • Cuota Regional: Límite estricto de 4 vCPUs regionales en eastus2. La familia v7 (Standard_D2s_v7) cuenta con cuota aprobada y disponibilidad en zonas.
    • Colisión de Red (ServiceCidrOverlapExistingSubnetsCidr): Azure asigna 10.0.0.0/16 por defecto a Services en Overlay. Al residir la VNet en 10.0.0.0/16 y la subred de AKS en 10.0.1.0/24, se producía solapamiento; el desacoplamiento a 172.16.0.0/16 garantiza aislamiento total.
    • Tensión de Cuota vs. PDB (minAvailable: 2) y Upgrades: Con cuota de 4 vCPUs (2 nodos), un upgrade con maxSurge: 1 falla por QuotaExceeded (intenta 3er nodo transitorio de 2 vCPUs alcanzando 6 vCPUs). La estrategia in-place (maxSurge: 0) solo es viable con 2 nodos activos (min_count = 2); en clúster de 1 solo nodo generaría un deadlock insalvable al no poder drenar pods respetando el PDB.

1. GitOps con ArgoCD y Plataforma de Autoservicio con Crossplane

Gobernanza declarativa pull-based con ArgoCD, Internal Developer Platform (IDP) con Crossplane, Workload Identity (OIDC), promoción automatizada cross-repositorio y gestión de secretos en AKS.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 05: Pipeline CI/CD Desacoplado por Jobs Concurrente en GitHub Actions

  • Estado: Aceptado e Implementado.
  • Decisión: Separar el flujo en jobs independientes (validate-fmt, tflint, security-checkov, infracost, terraform-plan, apply). Permite paralelismo masivo, feedback rápido en PRs y visibilidad granular de compuertas.

📌 ADR 07: Bootstrap Automatizado de ArgoCD mediante Terraform Helm Provider

  • Estado: Aceptado e Implementado.
  • Decisión: Desplegar ArgoCD de forma automatizada e idempotente desde Terraform con helm_release.argocd en namespace argocd. Configurado en Single-Replica (~500 MB RAM) desactivando Redis HA para maximizar el espacio libre en los nodos de trabajo.

📌 ADR 08: Compuertas de Seguridad DevSecOps para Repositorio GitOps

  • Estado: Aceptado e Implementado.
  • Decisión: Pipeline de CI en pleyades-gitops con 4 validaciones paralelas: yamllint, gitleaks, kubeconform (esquemas OpenAPI de K8s y CRDs) y trivy config (auditoría CIS Benchmark). Al ser GitOps puro con auto-sync, el CI en PR es la única compuerta de seguridad antes de producción.

📌 ADR 09: Crossplane Azure Storage Provider con Workload Identity (OIDC) y Sync Waves

  • Estado: Aceptado e Implementado.
  • Decisión: Paquetes modulares por servicio (provider-azure-storage v2.8.4, ~300 MB RAM frente a 1.5–2 GB del paquete monolítico). Autenticación sin secretos estáticos vía Azure Workload Identity (OIDC) con uami-crossplane-pleyades. Orquestación con Sync Waves de ArgoCD: Wave 0 para Providers y Wave 1 para ProviderConfig.

📌 ADR 29: Pipeline de Promoción Automatizada Cross-Repository y Entrega Continua GitOps

  • Estado: Aceptado e Implementado.
  • Decisión: Desacoplamiento estricto de repositorios. Al integrar a main en pleyades-app, se publica imagen inmutable con commit SHA en GHCR, y el workflow clona pleyades-gitops, actualiza apps/app/deployment.yaml y abre automáticamente un Pull Request de promoción mediante Personal Access Token (PAT).

📌 ADR 32: Orquestación Declarativa de PostgreSQL Flexible Server con Crossplane

  • Estado: Aceptado e Implementado.
  • Decisión: Despliegue de provider-azure-dbforpostgresql v2.8.4 con credencial federada fic-crossplane-dbforpostgresql. Permite aprovisionar instancias FlexibleServer de Azure directamente como objetos nativos de Kubernetes sin intervención manual.

2. Ingeniería de Confiabilidad de Sitios (SRE) y Observabilidad

Monitoreo determinista de Golden Signals con Prometheus/Grafana, mitigación de riesgos de exposición perimetral, suite completa de pruebas k6 y Jobs nativos in-cluster.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 11: Stack SRE y Observabilidad con kube-prometheus-stack y Server-Side Apply

  • Estado: Aceptado e Implementado.
  • Decisión: Desplegar kube-prometheus-stack v68.4.4 bajo el patrón Cerebro Central vs Sensores Distribuidos:
    1. node-exporter como DaemonSet obligatorio en cada nuevo nodo aprovisionado (~15 MiB RAM).
    2. Prometheus con Service Discovery centralizado a través de Cilium eBPF, persistencia Azure Disk (5 GiB) y retención de 12 horas (~600–750 MiB RAM total).
    3. Server-Side Apply: Habilitado en ArgoCD para eludir el límite de 262 KB de la anotación last-applied-configuration en los CRDs de Prometheus Operator.
    4. Mitigación terminatingReplicas (K8s 1.31+): Se declaró spec.ignoreDifferences en ArgoCD para ignorar el puntero JSON de terminatingReplicas y evitar el error ComparisonError.

📌 ADR 20: Observabilidad con Prometheus y Middleware Desacoplado

  • Estado: Aceptado e Implementado.
  • Decisión: Decorador HTTP transparente que intercepta códigos de estado y expone métricas en GET /metrics sin contaminar la capa de dominio:
    • http_requests_in_flight: Concurrencia activa (detección temprana de saturación).
    • http_request_duration_seconds: Histograma de latencias para percentiles críticos (p50, p95, p99).
    • http_requests_total: Contador por verbo, ruta y código de respuesta HTTP.

📌 ADR 22: Suite Modular de Pruebas de Rendimiento k6 y Modelo de Capacidad vs. SLOs

  • Estado: Aceptado e Implementado.
  • Decisión: Cuatro escenarios de prueba desacoplados (Load, Stress, Soak, Spike) con ejecución in-cluster mediante un Kubernetes Job (apps/app/k6-load-test-job.yaml) contra el ClusterIP interno, aprovechando el balanceo eBPF de Cilium y eliminando el cuello de botella del túnel SPDY de kubectl port-forward.
  • SLOs Certificados por Ley de Little:
    • 1 Solo Nodo (~25 req/s): $R = \frac{50}{25} - 0.1 = \mathbf{1.90\text{ s}}$ tiempo medio $\implies$ SLO formal: $p95 < 2500\text{ ms}$.
    • Producción Multi-Nodo (2 Nodos con min_count = 2, ~43 req/s): $R = \frac{50}{43} - 0.1 = \mathbf{1.06\text{ s}}$ tiempo medio $\implies$ SLO cumplido: $p95 < 1500\text{ ms}$ y $p99 < 2000\text{ ms}$.
    • Endpoints I/O Puro: SLO $p95 < 50\text{ ms}$.

📌 ADR 35/36: Deshabilitación de Ingress HTTP y Aislamiento por Port-Forwarding

  • Estado: ADR 35 reemplazado por ADR 36 (Aceptado e Implementado).
  • Decisión: Por principio de Defensa en Profundidad y Secure-by-Default (CWE-319), se vaciaron declarativamente las rutas HTTP del Ingress Controller (resources: []). El acceso a consolas administrativas (ArgoCD en localhost:8081, Grafana en localhost:3000) y pruebas de API se restringe a túneles cifrados kubectl port-forward, proyectando en roadmap la terminación TLS obligatoria con cert-manager y Let's Encrypt.

1. Arquitectura Hexagonal y Microservicio Core en Go 1.24

Arquitectura Limpia Hexagonal (Domain, Ports, Adapters), biblioteca estándar `net/http` de Go 1.24, pipeline de middlewares transversales, criptografía segura, mitigación de timing attacks y compuertas DevSecOps.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 01: Trunk-Based Development y Staging Granular (Anti-`git add .`)

  • Estado: Aceptado e Implementado.
  • Decisión: Ramas de corta duración integradas a main vía squash PRs. Formato estricto: <rama> -> <accion>: <explicacion>. Prohibido el uso de git add ., forzando commits atómicos por componente.

📌 ADR 12: DevSecOps Quality & Security Gates en Microservicio Go

  • Estado: Aceptado e Implementado.
  • Decisión: 7 compuertas en CI: detección de secretos (gitleaks), SAST (golangci-lint con gosec), pruebas unitarias (go test), SCA (govulncheck + trivy fs), seguridad de contenedores (trivy image), DAST dinámico (OWASP ZAP API Scan) y SonarCloud Quality Gate.

📌 ADR 13: Arquitectura Limpia Hexagonal (Ports & Adapters)

  • Estado: Aceptado e Implementado.
  • Decisión: Cero frameworks web pesados; uso exclusivo de net/http estándar de Go. Estructura desacoplada:
    • internal/domain: Entidad User, invariantes de negocio puras y errores centinela.
    • internal/ports: Contratos abstractos (UserRepository, PasswordHasher, TokenService).
    • internal/usecase: Orquestación pura (RegisterUserUseCase, LoginUserUseCase).
    • internal/adapters: http/ (handlers y DTOs), postgres/ (pgx/v5), crypto/ (Bcrypt y JWT).
    • cmd/pleyades-app/main.go: Composition Root exclusivo.

📌 ADR 15: Configuración Cloud-Native "Fail-Fast" (12-Factor App)

  • Estado: Aceptado e Implementado.
  • Decisión: Tolerancia dual local/cloud. En producción, las variables sensibles se inyectan vía ConfigMap/Secret de Kubernetes. Si falta cualquier variable requerida (DB_PASSWORD, JWT_SECRET), el proceso aborta inmediatamente en el arranque (*Fail-Fast*). Cero contraseñas por defecto en código fuente.

📌 ADR 16: Principio de Responsabilidad Única (SRP) en Handlers HTTP

  • Estado: Aceptado e Implementado.
  • Decisión: Segregación estricta de DTOs (RegisterUserRequest, UserResponse). La contraseña jamás se transmite en las respuestas. Mapeo determinista de errores centinela a códigos HTTP (201, 400, 401, 403, 409, 500).

📌 ADR 17: Criptografía Bcrypt y Mitigación de Timing Attacks (SOLID)

  • Estado: Aceptado e Implementado.
  • Decisión: Hashing Bcrypt con costo 10 (~70 ms de CPU por operación).
    • Mitigación Activa: El puerto expone CompareDummy(password) con secreto efímero en memoria generado vía CSPRNG (crypto/rand), garantizando que usuarios inexistentes consuman exactamente ~70 ms de CPU, neutralizando la inferencia estadística de usuarios válidos (OWASP A07:2021) sin secretos estáticos en código (SonarCloud go:S6437).

📌 ADR 18: Resolución Estricta de Alertas SAST en DDL Dinámico

  • Estado: Aceptado e Implementado.
  • Decisión: Cero #nosec. Como PostgreSQL no admite parámetros posicionales ($1) para sentencias DDL (CREATE DATABASE, REVOKE CONNECT), se autoriza // NOSONAR para go:S2077 sustentada en **4 controles compensatorios**:
    1. Validación por lista blanca regex: slug acotado estrictamente de 3 a 30 caracteres.
    2. Prevención de truncamiento (NAMEDATALEN = 64): slug de máx 30 caracteres impide alcanzar los 63 bytes del motor, eliminando colisiones.
    3. Delimitación con comillas dobles: "CREATE DATABASE \"%s\"" forzando identificador literal.
    4. Comentario de auditoría auditable.

📌 ADR 19: Graceful Shutdown en Kubernetes

  • Estado: Aceptado e Implementado.
  • Decisión: Intercepción de SIGTERM con ventana de gracia defensiva de 10 segundos: drena conexiones en vuelo, finaliza transacciones en PostgreSQL y apaga el proceso ordenadamente sin respuestas 502/504 (*Zero-Downtime Deployments*).

📌 ADR 23: Pipeline de Middlewares Transversales

  • Estado: Aceptado e Implementado.
  • Decisión: Composición modular Chain(h, middlewares...): métricas Prometheus, autenticación JWT con Sliding Session Renewal (cabecera X-Renewed-Token), Token Bucket Rate Limiting (20 req/s, burst 50) e Idempotencia (Idempotency-Key).

📌 ADR 27: Documentación Swagger UI Embebida

  • Estado: Aceptado e Implementado.
  • Decisión: Generación declarativa con swaggo/swag en /swagger/index.html con botón interactivo **Authorize** para probar endpoints protegidos con BearerAuth JWT e Idempotencia.

📌 ADR 28: Contenerización Multi-Stage Distroless (10.3 MB)

  • Estado: Aceptado e Implementado.
  • Decisión: Runtime sobre gcr.io/distroless/static-debian12:nonroot (UID 65532). Cero shells, cero package managers, imagen final de 10.3 MB en GHCR con 0 vulnerabilidades High/Critical en escaneos Trivy.

2. Multi-Tenancy Estricto (Database-per-Tenant) y Sharding Dinámico

Aislamiento físico y lógico Database-per-Tenant, erradicación de fuga cruzada con revocación de privilegios públicos, dimensión matemática del pool de conexiones frente a HPA y rotación de credenciales Show-Once.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 10: In-Cluster PostgreSQL StatefulSet vs Retiro en AKS

  • Estado: Retirado en AKS (reemplazado por ADR 30); mantenido solo para dev local.
  • Decisión: StatefulSet con disco administrado managed-csi (5 GiB) y PGDATA=/pgdata para evitar fallo de lost+found en ext4. En producción en AKS, fue formalmente escalado a 0 réplicas tras la provisión de Azure PostgreSQL Flexible Server para prevenir split-brain.

📌 ADR 14: Dimensión del Pool de Conexiones frente a HPA y Cuotas de Tenants (Fuente de Verdad)

  • Estado: Aceptado e Implementado.
  • Decisión: Parametrizar en Go (pgx/v5):
    • DB_MAX_OPEN_CONNS = 3 conexiones por pod (decisión final vigente que prevalece sobre el valor histórico de 4).
    • DB_MAX_IDLE_CONNS = 3 conexiones por pod.
    • CONNECTION LIMIT 2 por cada tenant en PostgreSQL (ALTER ROLE "usr_<slug>" CONNECTION LIMIT 2;).
  • Aritmética Defensiva del Servidor B1ms (35 conexiones utilizables):
    • Tope de 7 tenants a 2 conns = 14 conexiones reservadas.
    • Presupuesto para la app: $35 - 14 = \mathbf{21\text{ conexiones}}$.
    • Nominal (3 pods): $3 \times 3 = 9$ conns ($9 + 14 = 23 \implies \mathbf{12\text{ libres / 34\% margen}}$).
    • Pico HPA (5 pods): $5 \times 3 = 15$ conns ($15 + 14 = 29 \implies \mathbf{6\text{ libres / 17\% margen}}$).
    • RollingUpdate en pico (6 pods transitorios): $6 \times 3 = 18$ conns ($18 + 14 = \mathbf{32\text{ conns}} \implies \mathbf{3\text{ libres / 8.5\% permanente}}$). Imposibilita el desbordamiento too many clients already.

📌 ADR 25: Aislamiento Lógico (Database-per-Tenant) y Cota de Longitud de Slug

  • Estado: Aceptado e Implementado.
  • Decisión: Base de datos dedicada (tenant_<slug>) y usuario exclusivo (usr_<slug>).
    • Aislamiento Estricto: Ejecución obligatoria de REVOKE CONNECT ON DATABASE "tenant_<slug>" FROM PUBLIC; antes de asignar privilegios al usuario. Si un tenant intenta conectar a otro, PostgreSQL aborta con FATAL: permission denied for database.
    • Cota contra Truncamiento (NAMEDATALEN = 64): Slug acotado de 3 a 30 caracteres (regex ^[a-z][a-z0-9-]{1,28}[a-z0-9]$), garantizando que el nombre generado (máx 37 caracteres) quede lejos del límite de 63 bytes del motor, erradicando colisiones.

📌 ADR 26: Patrón Show-Once de Credenciales Efímeras y Endpoint de Rotación

  • Estado: Aceptado e Implementado.
  • Decisión: La contraseña de la BD del tenant se genera con CSPRNG (16 bytes hex), se devuelve en el JSON HTTP 201 Created una sola vez y nunca se persiste en la BD de metadatos (Zero Trust). Si se extravía, el propietario puede regenerarla en POST /api/v1/tenants/{id}/reset-password bajo autorización JWT.

📌 ADR 31: Sharded Database Server Pools (Bin-Packing de 5 a 7 Tenants)

  • Estado: Aceptado e Implementado.
  • Decisión: Catálogo centralizado en tabla database_pools. Algoritmo de bin-packing que asigna tenants al pool activo con menor carga hasta alcanzar 7 tenants, marcando el pool como FULL y activando la provisión de nuevas instancias.

Protocolo de Verificación de Aislamiento de Inquilinos

# Intentar conectar como usr_acmecloud a tenant_orioncorp en PostgreSQL:
psql "host=localhost port=5432 user=usr_acmecloud dbname=tenant_orioncorp"

# Salida esperada del motor (Rechazo determinista por REVOKE CONNECT FROM PUBLIC):
# psql: error: connection to server at "localhost" (127.0.0.1), port 5432 failed:
# FATAL: permission denied for database "tenant_orioncorp"
# DETAIL: User does not have CONNECT privilege.

3. Aprovisionamiento Just-in-Time y Warm Pool Preventivo

Auto-escalado horizontal de servidores relacionales gestionados, amortiguamiento preventivo de los tiempos de encendido en Azure (~6 a 14 min), determinismo en Kubernetes API y manejo idempotente de concurrencia.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 33: Warm Pool Provisioning con Kubernetes REST Trigger y RBAC Mínimo

  • Estado: Aceptado e Implementado.
  • Decisión: Umbral preventivo PoolScaleThresholdTenants = 5 (de 7 slots). Al registrar el 5.º inquilino, el provisionador shardeado evalúa si existe otro pool activo; si no existe, invoca K8sPoolScaleTrigger con cliente HTTPS nativo en Go sobre net/http proyectando credenciales del ServiceAccount, comunicándose directamente con la API REST de Kubernetes sin librerías pesadas como client-go.
  • Seguridad RBAC Segregada: ClusterRole exclusivo para CRDs de Crossplane (flexibleservers.dbforpostgresql.azure.upbound.io) y Role específico en crossplane-system para lectura de connection secrets, impidiendo el acceso a secretos administrativos.
  • Tope de Costes (Cost Cap): Límite máximo de pools activos (MaxAllowedPools = 3) para mitigar riesgos de denegación de servicio económico (EDoS).

📌 ADR 34: Verificación Operacional E2E con Crossplane

  • Estado: Aceptado e Implementado y Verificado Operacionalmente.
  • Decisión & Evidencia: Creación secuencial de inquilinos (acmecloud, orioncorp, solaris, andromeda, nebula). Al registrar el 5.º, el provisionador disparó psql-pleyades-dev-02 vía API de Kubernetes, reconciliado por Crossplane en Azure Central US.

Mecánica del Warm Pool y Amortiguamiento

Tenant 1..4 (Inmediato)   ──► Asignados a Pool 1 (Server 1)
Tenant 5     (Inmediato)   ──► Asignado a Pool 1 + Dispara CRD psql-pleyades-dev-02 (Azure ~6-14 min)
Tenant 6 & 7 (Inmediato)   ──► Absorción en los 2 slots restantes de Pool 1 (Cero espera de usuario)
Tenant 8 (Si Server 2 OK)  ──► Asignado a Pool 2 (Server 2) de forma transparente
Tenant 8 (Si Server 2 Pen) ──► HTTP 503 / 429 con Retry-After: 120 (Protección Fail-Safe)

Garantías de Idempotencia ante Concurrencia

Si dos inquilinos cruzan el umbral en milisegundos, ambas peticiones intentan crear el CRD determinista (psql-pleyades-dev-02). La primera responde 201 Created; la segunda recibe 409 Conflict. El adaptador captura el 409 como un éxito idempotente, garantizando que jamás se creen servidores duplicados en Azure.

4. Modelo Físico de Capacidad y Ley de Little

Dimensionamiento de recursos en Kubernetes (CFS Quotas), mitigación de CPU throttling, modelación matemática SRE mediante la Ley Interactiva de Little en sistemas cerrados y armonización con HPA y PDB.

Decisiones de Arquitectura del Dominio (ADRs)

📌 ADR 37: Declaración Formal de HPA, PDB y Estrategia RollingUpdate

  • Estado: Aceptado e Implementado.
  • Decisión Técnica:
    1. HPA (3 a 5 réplicas): Métrica de utilización media al 70% sobre requests.cpu: 100m. Al consumir Bcrypt ~70ms continuos, una sola petición por segundo satura el umbral de 70m y activa el autoescalado.
    2. Límites y Mitigación de CFS Throttling: Fijados en limits.cpu: 800m (0.8 vCPU por pod, PR #34). Con 5 pods en 2 nodos Standard_D2s_v7 (min_count = 2), descontando 0.4–0.6 vCPUs de pods de plataforma y el tope CFS de 1.6 vCPUs en el nodo con 2 pods, la app aprovecha $\approx \mathbf{3.0\text{ a }3.2\text{ vCPUs útiles}}$ ($\approx \mathbf{43\text{ a }46\text{ hashes/s}}$).
    3. PodDisruptionBudget (minAvailable: 2): Garantiza que durante drenados o actualizaciones de nodos el servicio jamás opere con menos de 2 réplicas saludables.
    4. RollingUpdate: maxSurge: 1 y maxUnavailable: 0. En escala máxima de 5 pods con surge transitorio de 6 pods ($6 \times 3 = 18$ conns) sumado a los 7 tenants ($14$ conns), el consumo total es de $\mathbf{32\text{ conns}}$ sobre 35 utilizables, garantizando **3 slots libres permanentes (8.5% de margen)** en el Flexible Server B1ms.

Modelación Matemática: Ley de Little en Sistemas Cerrados

En un sistema cerrado con $N$ Virtual Users, think-time $Z = 0.1\text{ s}$, y throughput $\lambda$, el tiempo de respuesta medio total del sistema $R$ se despeja como:

$$R = \frac{N}{\lambda} - Z$$

(Nota: R ya incluye tanto la espera en cola como el tiempo de servicio de Bcrypt y BD/red)

[1 NODO: Standard_D2s_v7, ~25 req/s]
R = (50 / 25) - 0.1 = 2.0 - 0.1 = 1.90s tiempo total medio  ──► SLO: p95 < 2500 ms

[2 NODOS: min_count = 2, ~43 req/s útiles]
R = (50 / 43) - 0.1 = 1.16 - 0.1 = 1.06s tiempo total medio ──► SLO: p95 < 1500 ms (p99 < 2000 ms)

3. Guía de Bootstrap, Runbooks Operativos y FinOps

Comandos reproducibles en PowerShell para aprovisionar, verificar y operar el clúster AKS, el backend de Terraform, la identidad OIDC, y protocolos FinOps de ahorro de costos.

Protocolos FinOps: Apagado y Encendido del Clúster

Para optimizar costos durante períodos de inactividad, el clúster se apaga desasignando el cómputo (costo 0 en VMs), preservando discos y configuraciones.

Procedimiento de Apagado (Stop)

Mitigación Webhook de Crossplane: Crossplane instala un webhook de validación (crossplane-no-usages). Azure AKS bloquea preventivamente az aks stop si detecta este webhook para evitar congelamiento del plano de control en el reinicio. Se debe eliminar el webhook antes de ordenar la parada:

# 1. Eliminar webhook de validación de Crossplane:
kubectl delete validatingwebhookconfiguration crossplane-no-usages

# 2. Detener cómputo de AKS (las VMs se desasignan, no cobran CPU/RAM):
az aks stop --name aks-pleyades-dev --resource-group rg-pleyades-dev

Procedimiento de Encendido (Start)

# Reanudar clúster (tarda 2-3 minutos en reactivar nodos y pods base):
az aks start --name aks-pleyades-dev --resource-group rg-pleyades-dev
