1. Resumen general

⚠️
Estado del Proyecto: Fuera de Producción / Archivado. La infraestructura activa fue desmantelada al concluir el ciclo de evaluación y entrega; esta documentación preserva la arquitectura, decisiones de hardening y bitácora técnica de lecciones aprendidas.

VPS única (4 GB de RAM) alojando el stack completo del proyecto Idempotencia: un producto gestor de bases de datos para usuarios finales (por eso corren 4 motores de DB). Incluye frontend, backend (producción y QA), y cuatro bases de datos, todo detrás de Nginx Proxy Manager (NPM) con SSL de Let's Encrypt. El acceso administrativo (SSH, bases de datos, paneles internos) está cerrado al público y se gestiona mediante Tailscale (VPN privada) y port knocking.

IP pública de la VPS: 46.224.101.88    IP privada (Tailscale) de la VPS: 100.99.206.50

Modelo de producto: los usuarios finales de Idempotencia necesitarán conectar sus propias herramientas externas (Airflow, DBeaver, etc.) directamente a bases de datos gestionadas, con credenciales propias — no solo a través de la app web. Esto implica que, a futuro, algunos puertos de base de datos deberán exponerse de forma controlada (ver Pendientes abiertos).

2. Firewall — estado actual y hallazgo crítico

2.1 Hallazgo de seguridad: Docker bypassea ufw

Se descubrió que Docker inyecta sus propias reglas en iptables (cadenas DOCKER / FORWARD) al publicar un puerto con ports: "0.0.0.0:PUERTO:PUERTO" en un docker-compose.yml. Estas reglas son independientes de ufw y se evalúan aparte — por lo que un puerto podía estar públicamente accesible desde internet aunque ufw status no mostrara ninguna regla ALLOW para él. Es un conflicto conocido entre Docker y ufw.

Esto se confirmó como la causa de un ataque de fuerza bruta real detectado contra el usuario sa de SQL Server, pese a que el diseño original asumía que ese puerto ya estaba restringido solo a Tailscale.

Método de verificación en 3 capas (auditoría obligatoria ante dudas de exposición):

docker ps                                          # qué publica Docker
sudo ss -tulnp                                      # qué escucha realmente el host
timeout 2 bash -c "echo > /dev/tcp/46.224.101.88/<puerto>" && echo "ABIERTO" || echo "cerrado"

2.2 Patrón de corrección aplicado

En cada docker-compose.yml afectado, cambiar:

# Inseguro:
ports:
  - "0.0.0.0:PUERTO:PUERTO"

# Corregido y aislado:
ports:
  - "100.99.206.50:PUERTO:PUERTO"   # solo accesible vía Tailscale

Y recrear con: docker compose up -d --force-recreate <servicio>. Esto no afecta la comunicación interna entre contenedores (que usa el nombre de contenedor sobre la red Docker red-proxy, no el binding público), ni requiere tocar volúmenes.

2.4 Hardening base del sistema

  • PermitRootLogin no, PasswordAuthentication no (solo login por llave SSH Ed25519/RSA).
  • Usuario dedicado devop con permisos sudo controlados.
  • fail2ban activo (jail sshd).
  • CrowdSec instalado como capa de detección y bloqueo activo en kernel.
  • unattended-upgrades instalado para parches automáticos de seguridad.

3. Acceso remoto

3.1 SSH — Port knocking

El puerto 22 permanece cerrado por defecto en el firewall. Para conectarse:

  1. Se ejecuta el script PowerShell (conectar.ps1) que:
    • Envía una secuencia de paquetes TCP a los puertos 7000, 8000, 9000 para abrir el 22.
    • Lanza automáticamente la sesión SSH con llave privada autorizada.
    • En segundo plano, tras un tiempo de espera configurable (15s), envía otra secuencia (6000, 5000, 4000) para volver a cerrar el puerto en iptables — sin interrumpir la sesión establecida.
  2. Cada miembro del equipo con acceso requiere su propia llave autorizada en ~/.ssh/authorized_keys de la VPS.

4. GitHub / control de versiones

4.1 Organización

Organización dedicada donde solo el rol DevOps (Juan) cuenta con privilegios administrativos.

4.2 Estrategia de ramas

feature/* ──► develop ──► QA ──► main
  • main: producción, desplegada automáticamente en la VPS vía GitHub Actions.
  • QA: ambiente de pruebas también desplegado en la VPS en puertos dedicados.
  • Solo los roles QA y DevOps tienen permiso de push/merge a main y QA.

4.3 Branch protection rules

  • Pull request obligatorio antes de mergear.
  • Restricción de push y merge limitada al team qa-devop.
  • Bloqueo estricto de force-push y eliminación de ramas críticas.

8. Incidentes resueltos (bitácora)

8.1 Error 500 en /auth/register — connection string con IP pública

Síntoma: Timeout de conexión SQL (SqlException) al registrar un usuario.

Causa: La connection string apuntaba a Server=46.224.101.88 en vez de Server=idempotencia-sqlserver, cayendo en un bloqueo por hairpin NAT.

Solución: Corregir el servidor al nombre del contenedor en la red Docker. Conexión restablecida de inmediato con latencia <1ms.

8.2 Volumen duplicado de SQL Server al recrear el contenedor

Síntoma: Al aplicar --force-recreate, Docker creó un nuevo volumen vacío ocultando los datos reales por discrepancia en el nombre de la carpeta.

Solución: Backup preventivo inmediato vía T-SQL (.bak), extracción de los 8 procedimientos almacenados, purga del volumen vacío y declaración explícita de volumen externo:

volumes:
  sqlserver-data:
    external: true
    name: idempotencia-db_sqlserver-data

Resultado: Cero pérdida de datos.

8.3 appsettings.json montado como directorio

Docker crea un directorio si el archivo no existe en el momento del primer bind mount. Corregido eliminando la imagen y reconstruyendo con docker compose build --no-cache.

8.4 Permisos del appsettings.json (chmod 600 vs 644)

El proceso dentro del contenedor corre como usuario no-root app. Un permiso 600 bloqueaba su lectura. Se ajustó a 644 montado como solo lectura.

9. Backups y persistencia

Respaldos realizados (ad-hoc):

  • Backup completo de SQL Server (.bak) en /home/devop/idempotencia-db-sqlserver/.
  • Exportación de stored procedures de negocio en texto plano (sps_backup.sql).

Se encuentra planificada la automatización de respaldos periódicos vía cron para los 4 motores hacia almacenamiento externo.

10. Pendientes abiertos

  • Alta prioridad: Parametrizar la IP de Tailscale vía secrets y cerrar puertos de QA al exterior.
  • Media prioridad: Backups automatizados recurrentes y persistencia de DataProtection Keys.
  • Mediano plazo: Migrar la lógica de negocio de la base master a una base de datos dedicada (idempotencia_app).

11. Kubernetes — evaluado y descartado por ahora

Se evaluó migrar los contenedores a Kubernetes (k3s). Conclusión técnica: no es viable en el servidor actual. La VPS es un solo nodo físico de 4 GB de RAM, y K8s consume entre 1.0 y 1.4 GB únicamente para su plano de control (API server, etcd, kubelet) sin aportar tolerancia a fallos entre máquinas.

Se continuará con Docker Compose optimizado y se reevaluará Kubernetes gestionado solo si el proyecto escala a múltiples servidores físicos.

12. Lecciones operativas (referencia rápida)

  • Docker bypassea ufw al publicar puertos: verificar siempre con ss -tulnp y pruebas TCP reales.
  • Las cadenas de conexión dentro de contenedores deben usar siempre el nombre del contenedor, nunca IPs públicas.
  • Antes de un --force-recreate con datos persistentes, verificar con docker inspect cuál es el volumen en uso y declararlo external: true.
  • Un contenedor en estado "Up" no garantiza servicio: validar con logs y pruebas de conexión internas.

Polaris — Plataforma ETL sobre Kubernetes Self-Managed en AWS

Plataforma integral de orquestación de datos e infraestructura como código construida sobre Kubernetes autoadministrado en AWS (K3s), con red Cilium (eBPF), empaquetado en Helm y pipeline ETL de Airflow desacoplado con Git-Sync.

¿Qué es Polaris?

Polaris es un proyecto de portafolio construido con el objetivo de demostrar dominio práctico de Kubernetes, Helm y Cilium en un entorno de datos real. A diferencia de un tutorial aislado, Polaris resuelve un problema de datos real de principio a fin, sobre una infraestructura completa desplegada en AWS y administrada por mí mismo (self-managed), no sobre un servicio gestionado como EKS.

Proyecto individual, desarrollado en aproximadamente dos semanas, sin equipo — desde el diseño de la infraestructura hasta el pipeline ETL funcional de punta a punta.

El Problema de Negocio

El punto de partida es un dataset público de Kaggle (Brazilian E-Commerce de Olist) con condiciones típicas de un entorno de datos real y no controlado:

  • Formatos erróneos: columnas con tipos de datos inconsistentes entre archivos CSV.
  • Datos incompletos: valores nulos y registros parciales en pagos y clientes.
  • Datos desestructurados: información que requiere normalización antes de ser analizable.

Mi Rol

  • DevOps / DevSecOps: diseño y automatización de la infraestructura (Terraform + Ansible), plataforma de Kubernetes y controles de seguridad automatizados en CI/CD.
  • Ingeniero de Datos: diseño del modelo analítico estrella en PostgreSQL, desarrollo de scripts ETL y definición de DAGs en Apache Airflow.

Por qué K3s self-managed y no EKS

  1. Costo: administrar el control plane directamente sobre EC2 evita el cargo fijo mensual por clúster que cobra AWS EKS.
  2. Aprendizaje real: operar K3s desde cero — bootstrap del control plane, unión de workers, instalación de CNI Cilium, gestión de storage EBS CSI — obliga a entender los fundamentos que un servicio gestionado abstrae.

Capa Responsabilidad Repositorio
Infraestructura VPC, subnets, EC2, IAM, EBS y bootstrap de K3s con Ansible polaris-infrastructure

Infraestructura — Metodología de Trabajo

Estrategia de desarrollo sistemática: paso de configuración manual validada a automatización reproducible con Ansible y Terraform.

Secuencia: Manual → Documentado → Automatizado

  1. Configurar manualmente primero: instalación y prueba directa en instancias EC2 (K3s, Cilium, runner, deploy key) hasta llegar a un estado saludable.
  2. Documentar cada paso validado: registro exacto de paquetes, variables de entorno y comandos necesarios.
  3. Traducir a roles de Ansible (CaC): estructuración de 6 roles ordenados en site.yml (k8s_master, k8s_worker, helm, ebs_csi_driver, github_runner, deploy_key).

Inyección de Secretos sin Ansible Vault

Los secretos que requiere Ansible (PAT de GitHub, IP de control plane, llaves del CSI Driver) se inyectan como variables de entorno mediante lookup('env', ...) cargadas desde un archivo .env local excluido de Git.

⚠️
Trade-off consciente: Se priorizó la reproducibilidad desatendida (sin tener que desbloquear un vault interactivo en cada reconstrucción), sabiendo que en producción corporativa se optaría por HashiCorp Vault o AWS Secrets Manager.

1. Kubernetes y Cilium

SíntomaCausaSolución Técnica

Plataforma — Decisiones Técnicas

Helm con Valores Separados del Chart

Los charts upstream (Bitnami, Apache Airflow, Prometheus Community) se consumen directamente y las personalizaciones residen en charts/*/values.yaml. El pipeline descarga los charts, ejecuta helm lint y genera manifiestos en rendered/ para ser auditados por Checkov y Trivy.

Airflow Desplegado sin --wait

Airflow se despliega sin la bandera --wait de Helm para evitar un bloqueo circular con su hook de migración de base de datos. La verificación de salud se ejecuta posteriormente una vez completada la migración.

Almacenamiento Persistente EBS CSI

PostgreSQL, RabbitMQ y la observabilidad utilizan la StorageClass ebs-sc, permitiendo reprogramar pods de estado en cualquier nodo sin riesgo de pérdida de datos.

Plataforma — Seguridad y DevSecOps

La seguridad como condición inherente de entrega: escaneo estático, hardening de contenedores y TLS automático.

Controles en el Pipeline

  • YAMLLint & Helm Lint: sintaxis de manifiestos y charts.
  • Checkov: auditoría de seguridad sobre manifiestos renderizados.
  • Trivy: escaneo de vulnerabilidades; detiene el pipeline ante hallazgos CRITICAL o HIGH.
  • SonarCloud: cumplimiento del Quality Gate de código.

Hardening de Pods

  • Ejecución con usuario no root.
  • Perfil de seguridad seccompProfile: RuntimeDefault.
  • Capabilities de Linux eliminadas (drop: ALL) y restricción de escalado de privilegios.

Plataforma — CI/CD y Despliegue

Secuencia del Pipeline

YAMLLint ➔ Helm lint + render + Checkov ➔ Trivy + SonarCloud ➔ Deploy en Runner Self-Hosted ➔ Verificación de rollouts

Lección: Versionado Inmutable de Charts

El pipeline fija versiones explícitas para Airflow, PostgreSQL y RabbitMQ. Un upgrade de Helm sin versión fijada modificó en una ocasión volumeClaimTemplates (campo inmutable de StatefulSet), forzando la recreación del PVC. Fijar las versiones eliminó de raíz este riesgo.

Aplicación de Datos — Pipeline ETL (Olist)

El DAG olist_etl_pipeline procesa el dataset brasileño de comercio electrónico con ejecución lineal para garantizar integridad entre etapas.

Fases del Pipeline

  1. Extracción (kaggle_downloader.py): descarga mediante Kaggle CLI, omitiendo archivos ya presentes para evitar tráfico y redundancia.
  2. Transformación (clean_orders.py): casteo de tipos temporales, derivación de macro-regiones, agregación previa de pagos y reseñas por pedido para evitar duplicidad de filas, y validación estricta de cantidad de registros.
  3. Carga (postgres_loader.py): carga por lotes de 2.000 filas con cláusula ON CONFLICT DO NOTHING dentro de una transacción ACID con rollback ante fallos.

Aplicación de Datos — CI/CD y Operación en K8s

Controles de Calidad y Seguridad

  • UID 50000: la imagen no ejecuta procesos como root.
  • GitHub Actions fijadas por SHA: reducción de ataques de cadena de suministro.
  • SQL Parametrizado: uso estricto de psycopg2.sql y execute_values para prevenir inyección SQL.

Limitaciones Conocidas (Documentadas)

  • El DAG tiene schedule=None para dispararse de manera controlada.
